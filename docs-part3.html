Technical Explanation

4.1 How Each Requirement Was Implemented

✅
XML as Primary Data Store (xmldom)

Payments, messages, logs, and reservations are stored in XML files at backend/data/xml/. All reads use DOMParser and all writes use XMLSerializer from the xmldom library. Users, rooms, and groups use JSON files at backend/data/json/.

✅
XML Retained and Used for XSLT Reports

The same XML files used for live data (payments.xml, users.xml) are also the input for XSLT stylesheets in the Admin Reports dashboard — no separate sync step needed for most reports.

✅
XSLT Transformations

Three .xslt stylesheets transform XML to HTML reports and JSON. The xsltModel.js applies them via xslt4node with a DOM-based HTML fallback if the native engine is unavailable.

✅
Real-Time Messaging with Kafka

KafkaJS producer publishes to boardease.messages topic. Consumer reads and broadcasts via Socket.IO. Graceful fallback to direct emit when Kafka is offline.

✅
Payment Event Queue with RabbitMQ

amqplib connects to RabbitMQ, asserts a durable boardease.payments queue. Payment submissions publish events; the consumer emits payment_notification to the admin via Socket.IO.

✅
JWT Authentication

Login returns a signed JWT. The auth.js middleware verifies it on every protected route using jsonwebtoken.verify(). Passwords are hashed with bcryptjs before storage in users.json.

✅
File Uploads (Multer)

Multer handles multipart form data for payment proofs, room photos (up to 5), GCash QR codes, and profile avatars. Files are stored in backend/uploads/ and served as static assets at /uploads/<filename>. Frontend uses a ?t=timestamp cache-busting parameter so browsers always fetch the latest uploaded image.

✅
Docker Offline Deployment

All 6 services are containerized. Health checks on Kafka, RabbitMQ, and Redis ensure the backend only starts after its dependencies are ready. Named volumes persist uploads and XML data across restarts.

✅
Mobile Responsive Design

CSS Modules with breakpoints at 768px and 480px. iPhone SE (375px) tested. Viewport meta tag in _document.js. Sidebar becomes a slide-in drawer with hamburger toggle. All inputs use font-size: 16px to prevent iOS zoom.

✅
Activity Logging

Every auth event, payment action, message, and notification is automatically logged to backend/data/json/logs.json via logActivity(type, detail, ref). Viewable in the Admin Reports → Activity Logs tab.

✅
Public Landing Page & Tenant Self-Registration

The root route (/) serves an animated public landing page with live room stats. New tenants can self-register at /register without admin involvement, defaulting to the tenant role.

✅
Profile Pages with Avatar Upload & Password Change

Both admin (/admin/profile) and tenant (/user/profile) have dedicated profile pages supporting personal detail editing, avatar upload via Multer, and password change with current password verification.

4.3 Challenges Encountered and Solutions

1
Kafka Not Available in Local Dev
🔴 Problem
Running Kafka locally requires Zookeeper + Kafka broker setup. During development without Docker, the backend crashed when Kafka was unreachable.
✅ Solution
Wrapped initKafka() in a try-catch. Set kafkaReady = false on failure. In publishMessage(), if kafkaReady is false, return false and let the caller fall back to direct io.emit(). The app works identically with or without Kafka.
2
XML Too Complex for User Data Storage
🔴 Problem
Storing user accounts in XML caused significant friction. Auth operations like login require looking up a user by username and comparing a bcrypt hash — but with xmldom, this means parsing the entire XML document, iterating child nodes, and extracting text values manually for every field. Updating a user (e.g. changing avatar, password, or profile details) required finding the node by ID, then individually removing and replacing each child element. The verbosity made the auth and profile code error-prone and hard to maintain. Hashed passwords and avatar filenames also contained characters ($, ., /) that required CDATA wrapping to avoid breaking the XML structure.
✅ Solution
Migrated users (and rooms, groups) to JSON files. JSON.parse returns a plain JavaScript array — login becomes a simple .find(), updates become a spread merge, and no character escaping is needed. XML is kept for payments, messages, logs, and reservations where the XSLT report pipeline directly consumes the same files.
3
Browser Caching Stale Uploaded Images
🔴 Problem
After uploading a new profile photo or QR code, the browser continued showing the old image because it cached the previous response for the same URL path.
✅ Solution
Added a ?t=timestamp cache-busting query parameter to all upload image src attributes. A React state variable avatarTs / qrTs is updated to Date.now() after each successful upload, forcing the browser to fetch the new image.
3
XSLT Engine Unavailable on Some Environments
🔴 Problem
xslt4node requires native Java bindings which may not be available in all Node.js environments, causing the Reports page to fail entirely.
✅ Solution
xsltModel.js wraps the require('xslt4node') in a try-catch. If unavailable, it falls back to a pure JavaScript DOM-based HTML table builder using the same xmldom parser — producing visually identical output.
4
Mobile Layout Breaking on iPhone SE (375px)
🔴 Problem
The app was not scaling correctly on mobile — content was overflowing, the sidebar was not accessible, and iOS was auto-zooming on input focus.
✅ Solution
Created _document.js with the viewport meta tag (width=device-width, initial-scale=1). Set all inputs to font-size: 16px to prevent iOS zoom. Replaced fixed sidebar with a slide-in drawer triggered by a hamburger button in a fixed mobile topbar.
5
Kafka Broker URL Difference: Local vs Docker
🔴 Problem
Locally, Kafka is at localhost:9092. Inside Docker, the backend container must reach Kafka at kafka:9092 (service name). Using the wrong URL caused connection failures.
✅ Solution
The KAFKA_BROKER environment variable is set to localhost:9092 in .env for local dev, and overridden to kafka:9092 in docker-compose.yml for the containerized backend service.
6
Docker Service Startup Order
🔴 Problem
The backend started before Kafka and RabbitMQ were ready, causing connection errors on first boot.
✅ Solution
Added healthcheck blocks to Kafka, RabbitMQ, and Redis services. The backend service uses depends_on: condition: service_healthy so it only starts after all brokers pass their health checks.
7
Inline Styles Overriding Responsive CSS
🔴 Problem
Many dashboard pages used hardcoded inline styles like padding: "28px 32px" and gridTemplateColumns: "1fr 420px" which could not be overridden by media queries.
✅ Solution
Replaced fixed inline padding with smaller values (16px) that work on all screen sizes. Replaced fixed grid columns with repeat(auto-fit, minmax(min(100%, 300px), 1fr)) which naturally stacks on small screens.
